### (b) Screens that compute an amount, stock or status themselves

- **Inventory: `classifyStock()` derives "Low stock" / "Out of stock" in the browser** with a hard-coded threshold of 10 (a copy of the dashboard's SQL rule). `admin_list_inventory` returns only raw quantity and flags; there is no per-row state or low-stock filter. This conflicts with rule 3, and there is nothing in the backend to switch to. Per rule 8 I did **not** build a workaround or remove a working screen. I **kept** the behaviour and added an on-screen note on the Low/Out views saying it is worked out on the screen from the quantity (1 to 10 units) and that the database stores no stock status. Listed under "missing backend".
- Dashboard, orders, customers, payments, promotions: **no client-side totals or statuses found.** Money is formatted with `formatMoney` only. The only arithmetic in admin code is pagination page maths and turning typed shillings/percent into cents/basis points for an RPC argument (string-only, server re-validates).
- Not an issue but worth knowing: the Order value figure the dashboard returns is _not revenue_ (SQL says so). It is now shown with that exact caveat.

### (c) Frontend-only hiding without a working no-access state

- None found. The `/admin` shell asks the database (`is_admin` RPC). Every read screen already had a branch for a database refusal. Nav items are not filtered by role (there is no permission model; see §5), so nothing relies on hiding.
- Weak spots fixed: the 12 refusal branches were copy-pasted with no next step; the full-page denial had no sign-out; the wording could not tell staff from customers.

## 4. What the UI shows vs what the backend decides

| UI shows                                                  | Decided by                                                                                                |
| --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Dashboard counts, order value, payment counts, as-of time | `admin_dashboard_summary` (the UI only formats)                                                           |
| Payment status, amount, reference, failure                | `payment_transactions` via the read RPC; set by providers/server, never by the UI                         |
| Promotion list, live/inactive, uses                       | `admin_list_promotions`                                                                                   |
| Whether a promotion is created live                       | The admin's choice, sent as `is_active`; the database stores it and computes every discount at order time |
| Promotion value validity, code uniqueness, dates          | Database (UI pre-checks are for usability; `code_taken` shown on the code field)                          |
| Stock quantity                                            | Database. "Low/Out" badge on the inventory screen is a **screen-side display rule** (see 2b)              |
| Whether you may see/do anything                           | Database (`require_admin()` in every RPC, MFA gate). The UI only reacts.                                  |
| Page counts / "Showing a–b of n"                          | Database total; page arithmetic only                                                                      |

## 5. Authorization: how each screen behaves when the server refuses

The backend model is just `staff` and `admin`; the admin RPCs are **admin-only** (staff are refused) and the shell admits only admins. There is no per-permission matrix, so "a staff user lacking a permission" is simply a staff user, or an admin whose RPC is refused (not admin, or `mfa_required`). Nothing here grants anything.

| Situation                                                     | What the UI does                                                                                                                                                               | Seen in browser (mock)?     |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------- |
| Signed-in non-admin opens any `/admin` URL                    | Full-page "Admin access required" with Back to the store and Sign out. **No admin nav, no data.**                                                                              | Yes (customer)              |
| Staff user                                                    | Same page, wording says staff access does not include the admin area.                                                                                                          | Yes                         |
| A read is refused (42501 / `not_authorised` / `mfa_required`) | Shared no-access panel: "Nothing was loaded", Try again, Sign out. No rows, no cards, no partial data.                                                                         | Yes: dashboard and payments |
| Promotions list refused                                       | Same panel. Uses a purpose-written mapper because the existing `listPromotions` wrapper flattens every error to plain text.                                                    | **Type-checked only**       |
| An action is refused                                          | The plain message from the existing mapper (e.g. "You are not allowed to manage promotions."). Nothing changed, list refreshed.                                                | Yes: promotion toggle       |
| Offline read                                                  | "You appear to be offline" with Try again.                                                                                                                                     | Yes                         |
| Offline action                                                | "We couldn't reach the server, so nothing was changed." The action is **not** queued.                                                                                          | Yes                         |
| `mfa_required` vs plain refusal                               | Indistinguishable: both are SQLSTATE 42501 and every existing mapper collapses them. The no-access hint tells the person to sign in again if their role or two-factor changed. | n/a                         |
